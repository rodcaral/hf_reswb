QUICK FACTS
================================================================================

Defect Type: Data integrity (silent scale break)
Severity: High (affects data reliability)
Current Status: Dormant (no affected production Series yet)
Root Cause: Incremental import only re-fetches trailing window; basis changes applied retroactively by provider are never re-applied to historical data

Affected Providers:
  - Yahoo Finance (stock splits) -- rare for US large-caps; dividend-unadjusted close
    means ex-dividend dates don't trigger a rescale
  - FRED (economic indicator revisions)
  - CEDEAR/BYMA conversion-ratio changes -- higher frequency for this project's actual
    universe: quarterly regulatory reporting cadence (CNV RG 1142/2026) plus ad hoc
    local ratio changes; a confirmed real ~2:1 step exists in this database
    (2024-01-24). See CONSULTANT-PACKAGE-F009.md ("Trigger Frequency").
  - Any provider with basis-shift or revision behavior

When it occurs:
  1. Series is backfilled before a basis-changing event
  2. Event occurs (split, revision, etc.)
  3. Incremental import runs, fetching only from latest stored date forward
  4. Pre-event rows never re-fetched
  5. Post-event rows arrive already adjusted to new basis
  6. Result: permanent discontinuity with no marker/correction row

Why no corrections are fired:
  - Correction mechanism only fires when a re-fetched value differs from stored
  - Dates before the re-fetch window are never re-fetched
  - Therefore dates before the window can never produce a correction
  - Oldest ever-corrected observation: 4 days old (the re-fetch window)

================================================================================
REMEDY OPTIONS SUMMARY
================================================================================

Three approaches evaluated in detail in CONSULTANT-PACKAGE-F009.md:

R1: PERIODIC FULL-RANGE RE-FETCH
  Cost: High (bandwidth + rate limits)
  Coverage: Complete (catches all basis shifts)
  Use when: You need guaranteed accuracy, can afford bandwidth

R2: EVENT CAPTURE BACKFILL
  Cost: Medium (parsing, schema change, event backfill)
  Coverage: Partial (only splits/dividends/events, not silent revisions)
  Use when: You want to prevent future breaks without full re-fetch

R3: DETECT-AND-REFUSE CONSUMER-SIDE
  Cost: Low (heuristic detection only)
  Coverage: Defensive (gates against use, doesn't fix data)
  Use when: You want to prevent accidental use of broken data

See CONSULTANT-PACKAGE-F009.md for 2-page detailed evaluation.
